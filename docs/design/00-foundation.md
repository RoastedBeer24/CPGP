### 최우선 원칙: 그래픽보다 게임성
- 판단이 갈릴 때는 항상 **플레이가 더 재미있어지는 쪽**을 고릅니다. 그래픽 품질은 "읽기 쉽고 분위기가 전달되는" 수준이면 충분합니다.
- 시각 요소의 목표는 **가독성**입니다. 적과 엄폐물, 해킹 가능한 대상, 이동 경로가 한눈에 구분되어야 합니다.
- 그래서 개발 시간은 이동, 사격, 해킹, 선택의 결과처럼 **플레이어가 직접 만지는 것**에 먼저 씁니다.

## 2. 하이 콘셉트 (초안)

> **"몸을 빌려 쓰는 도시에서, 빚을 갚을 것인가 판을 뒤엎을 것인가."**

- **제목:** CyberUniverse
- **톤:** 진지한 누아르. 비, 네온, 고독, 도덕적으로 회색인 선택. 농담은 인물의 냉소 정도로만 둡니다.
- **배경:** 2080년대 해안 거대도시 **"네오 부산(Neo-Busan)"**. 국제 항만 위로 고가도로와 고층 주거 블록이 겹겹이 쌓이고, 그 위에 기업 타워가 섭니다. 항만은 밀수와 데이터 거래의 중심지입니다. 도시는 높이에 따라 계층이 나뉘고, 이 구조가 **수직 탐험**과 연결됩니다.
- **주인공:** 외형을 커스터마이즈할 수 있습니다. **출신은 세 갈래** 중 하나를 고릅니다(§2.1). 셋 모두 네오 부산 출신이 아니며, 각자의 사정으로 이 도시에 흘러듭니다. 도입부가 끝나면 기업에서 **사이버웨어를 리스(임대)**해 몸에 단 해결사가 됩니다. 할부를 못 내면 기업이 임플란트를 **원격으로 비활성화하거나 회수**합니다.
- **핵심 갈등:** 돈(빚)과 자유(해킹으로 리스 잠금 해제), 그리고 사람(동료와 세력) 사이의 선택입니다.

> 이 설정은 시스템과 직접 연결됩니다. 빚은 경제 시스템이 되고, 리스 잠금은 해킹과 성장 시스템이 되며, "누구 편에 설 것인가"는 선택과 평판 시스템이 됩니다.

### 2.1 출신 세 갈래

셋 모두 **네오 부산 바깥에서 살다가, 각자의 사정으로 이 도시에서 지내게 되는** 흐름입니다. 도입부는 "도시에 도착해 자리를 잡는 과정"이고, 출신에 따라 그 장면과 사정이 달라집니다.

출신은 **도입부 장면**, **고유 대화 선택지**, **NPC의 첫인상**만 바꿉니다. 능력이나 빌드에는 영향을 주지 않습니다.

| 출신 | 네오 부산 이전의 삶 | 도시에 오게 된 사정 (제안) |
|---|---|---|
| **공무원** | 다른 도시 행정기관의 하급 공무원. 서류와 절차, 관료의 말투를 앎 | 원치 않는 파견 발령, 또는 무언가를 피해 도망치듯 전출 |
| **부랑자** | 일정한 거처 없이 여러 도시를 떠돌던 사람. 사람을 읽고 버티는 법을 앎 | 일거리와 잠자리를 찾아 가장 큰 항만 도시로 흘러듦 |
| **스캐빈저** | 폐허와 폐기 구역에서 고철과 부품을 뜯어 팔던 사람. 기계를 보는 눈이 있음 | 부품을 제값에 팔 수 있는 곳, 항만의 암시장을 찾아옴 |

### 2.2 시작 임플란트: 생존의 기반
- 세 출신 모두 **똑같이 생존 유지용 임플란트 하나만** 가진 채 시작합니다. 예를 들면 오염된 공기를 걸러주는 호흡 필터나 혈액 정화기 같은 것입니다.
- 이 임플란트는 **초반에는 사실상 언급되지 않습니다.** 능력 보너스도 없고 UI에서도 눈에 띄지 않습니다. 너무 당연해서 아무도 신경 쓰지 않는 장기에 가깝습니다.
- 전투와 해킹에 쓰는 사이버웨어는 모두 도시에 온 뒤 **리스로** 얻습니다.

`[결정 필요]` 이 임플란트를 나중에 이야기의 열쇠로 쓸까요? 예를 들면 "알고 보니 이것도 리스 기업의 제품이었고, 회수 대상이었다" 같은 반전입니다. 아니면 끝까지 배경 설정으로만 둘까요?

## 3. 핵심 기둥 (Design Pillars)

네 가지 재미 축(전투, 해킹·잠입, 스토리·선택, 탐험·성장)을 **세 개의 기둥**으로 묶습니다. 기능을 추가할지 판단할 때 "이 기능이 기둥을 강화하는가?"를 기준으로 삼습니다.

### 기둥 1. 모든 문에는 세 개의 열쇠가 있다
**전투 · 해킹 · 잠입**
- 모든 목표에 최소 3가지 접근이 있습니다: **정면 돌파**(총·근접), **넷러닝**(원격 해킹), **우회**(잠입·대화·환경 이용).
- 세 방식은 서로 섞입니다. 예를 들어 카메라를 해킹해 끄고, 잠입으로 들어간 뒤, 들키면 전투로 전환합니다.

### 기둥 2. 몸이 곧 빌드다
**성장**
- 레벨업 수치보다 **사이버웨어 장착**이 플레이 방식을 바꿉니다. 이중 점프 다리, 단분자 와이어 팔, RAM 확장 OS 등이 예입니다.
- 리스 설정 덕분에 **강력한 임플란트에는 대가**(빚, 기업 추적)가 따릅니다.

### 기둥 3. 도시는 기억한다
**스토리 · 선택 · 탐험**
- 선택은 **세력 평판**, **구역 상태**(경비 강화, 상점 폐쇄 등), **NPC의 반응**으로 되돌아옵니다.
- 탐험 원칙은 **"넓이보다 밀도"**입니다. 작은 구역을 수직으로 촘촘하게 만들고, 숨은 경로와 데이터 조각, 사이드 의뢰를 곳곳에 둡니다.

## 4. 월드 구조: 구역형 반오픈월드

끊김 없는 하나의 거대한 맵 대신, 도시를 **여러 구역**으로 나눕니다. 데우스 엑스: 휴먼 레볼루션의 허브 구조와 비슷합니다.

- **구역 안에서는 자유롭게** 돌아다닙니다. 의뢰 순서, 접근 경로, 탐험 범위를 플레이어가 정합니다.
- **구역 사이 이동**은 엘리베이터, 지하철, 검문소 같은 **전환 지점**을 거치며 짧은 로딩을 둡니다.
- **구역의 종류**
  - **거점 구역:** 안전한 곳. 상점, 리퍼닥, 의뢰 중개인, 은신처가 있습니다. 전투는 없습니다.
  - **작전 구역:** 의뢰를 수행하는 곳. 경비, 적, 해킹 대상, 숨은 경로가 있습니다.
- **구역 상태가 저장됩니다.** 처치한 적, 열린 문, 바뀐 평판이 구역을 다시 찾아도 유지됩니다.

이 방식은 범위가 커지는 위험을 줄이고, 구역 하나하나를 촘촘하게 만들 수 있게 해줍니다. 엔진의 대형 맵 처리 기능에도 의존하지 않습니다.

## 5. 플레이 인원: 싱글 + LAN 코옵

기본은 **혼자서도 완결되는 싱글 플레이**이고, 같은 네트워크(LAN)에 있는 친구가 **합류할 수 있는** 구조입니다.

### 5.1 처음부터 멀티플레이를 염두에 두는 이유
멀티플레이는 나중에 붙이기가 가장 어려운 기능입니다. 싱글 전용으로 짠 코드를 나중에 코옵용으로 바꾸려면 거의 다시 써야 합니다. 그래서 **M1부터 모든 게임플레이 코드를 네트워크를 전제로** 작성합니다. 싱글 플레이는 "혼자 호스트하는 코옵"으로 처리해서, 두 방식이 같은 코드로 돌아가게 합니다.

### 5.2 기본 구조
- **호스트 방식:** 한 플레이어의 게임이 서버 역할을 겸합니다. 별도 서버는 없습니다.
- **판정은 호스트가:** 적 AI, 피해 계산, 해킹 성공 여부, 퀘스트 진행, 구역 상태는 호스트가 결정하고 다른 플레이어에게 전달합니다. 동기화가 어긋나는 문제를 줄이는 표준적인 방식입니다.
- **세이브:** 월드 진행(퀘스트, 평판, 구역 상태)은 **호스트의 세이브**에 저장됩니다. 캐릭터(출신, 외형, 사이버웨어, 인벤토리, 돈)는 **각 플레이어가 자기 것을 들고** 참여합니다.

### 5.3 코옵 때문에 달라지는 설계
| 요소 | 코옵에서의 처리 (제안) |
|---|---|
| 시간 감속 임플란트 | 세상 전체의 시간을 늦출 수 없으므로, **사용자 주변 적의 시간만 느려지는** 방식으로 구현. 싱글에서도 같은 방식이라 체감은 같음 |
| 일시정지 | 코옵 중에는 메뉴를 열어도 게임이 멈추지 않음 |
| 대화와 선택 | 대화를 시작한 플레이어가 선택. **메인 스토리의 결말 선택은 호스트**가 함 |
| 평판과 결과 | 월드에 남는 결과는 호스트 월드에 반영 |
| 난이도 | 참여 인원에 따라 적의 수와 체력을 조정 |
| 쓰러짐 | 즉사 대신 **다운 상태**. 동료가 일으켜 세울 수 있음 |

### 5.4 범위
- **포함:** LAN 안에서 방 만들기와 참여, 최대 인원 **2~4명**(슬라이스에서는 2명으로 검증)
- **제외:** 인터넷 매치메이킹, 전용 서버, PvP, 음성 채팅
- **검증 방법:** 이 개발 환경에서 게임을 두 개 띄워 서로 접속시키는 자동 테스트로 동기화를 확인합니다. 실제 두 PC 간 LAN 테스트는 사용자가 합니다.

## 7. 버티컬 슬라이스 범위

### 7.1 포함 (Must)
| 영역 | 내용 |
|---|---|
| 구역 | **거점 구역 1곳**(소형: 상점, 리퍼닥, 중개인, 은신처) + **작전 구역 1곳: "하역지구"**(약 250×250m, 지상·골목·옥상·지하 3~4층 구조). 구역 전환 1개 |
| 출신 | 세 출신 모두 선택 가능. "네오 부산에 도착하는" 공통 도입부에 출신별 장면과 대화를 다르게 둠 |
| 코옵 | LAN 방 만들기·참여, 2인 동시 플레이, 다운과 부활 |
| 이동 | 걷기, 달리기, 웅크리기, 슬라이딩, 벽 오르기(맨틀), 이중 점프(임플란트) |
| 전투 | **사이버펑크 2077식 RPG 슈터**. 무기 3종(권총, 산탄총, 팔 내장형 근접 블레이드), 히트스캔 사격, 반동, 부위별 피해, 장갑, 피해 수치 표시, 회피 대시, 시간 감속 임플란트 1종 |
| 적 AI | 3종: 일반 경비, 중장갑병, 적 넷러너(플레이어를 역해킹) |
| 잠입 | 시야 원뿔, 경계 단계(무경계 → 의심 → 수색 → 전투), 은신 제압, 시체 숨기기 |
| 해킹 | 스캔 모드, RAM 기반 퀵핵 4종(카메라 차단, 주의 분산, 과열, 무기 오작동), 장치 해킹(문, 포탑) |
| 성장 | 사이버웨어 슬롯 5부위, 리스 임플란트 8종, 인벤토리, 상점, 리퍼닥 |
| 서사 | 메인 의뢰 1개(결말 분기 2~3개), 사이드 의뢰 2개, 대화 트리와 능력·출신 체크 |
| 세력 | 2개 세력과 평판 수치. 평판에 따라 대화, 가격, 적대 여부가 바뀜 |
| 시스템 | 저장/불러오기, 일시정지, 설정(감도, 볼륨, 키 바인딩) |

### 7.2 제외 (Won't, 슬라이스 이후 검토)
차량, 끊김 없는 대형 맵(구역 간 로딩으로 대체), 낮/밤 사이클, 제작(크래프팅), 성우 음성, 로맨스, 인터넷 멀티플레이, 경찰 수배 시스템, 세밀한 캐릭터 외형 편집(슬라이스에서는 프리셋 몇 개)

> 제외 목록이 기능 목록만큼 중요합니다. 오픈월드 계열은 범위가 커지다 실패하는 경우가 가장 흔합니다.

### 7.3 에셋 정책: 공개 에셋만 사용
- **라이선스:** 무료로 공개된 에셋이면 라이선스 종류와 관계없이 사용합니다. 다만 라이선스마다 지킬 것이 다릅니다.
  - CC0(퍼블릭 도메인): 제약 없음
  - CC-BY: 크레딧에 출처 표기
  - 비상업 전용(NC): 이 에셋이 들어간 상태로는 **게임을 판매할 수 없음**. 나중에 상업화하려면 그 에셋만 교체
  - 개작 금지(ND): 원본 그대로만 사용(색이나 형태를 바꾸지 않음)
  - 재배포 금지 조건이 있는 에셋: 공개 저장소에 올리지 않고 받는 방법만 기록
- **주요 출처 후보**
  - 3D 모델: Kenney, Quaternius
  - 텍스처와 HDRI: Poly Haven, ambientCG
  - 효과음: Freesound(CC0 필터), Kenney Audio
  - 음악, 폰트, 기타: OpenGameArt, Google Fonts(OFL)
- **기록:** 사용하는 에셋마다 출처, 작가, 라이선스를 `docs/assets.md`에 기록하고, 게임 크레딧에도 표시합니다. 라이선스를 기록해 두면 나중에 상업화할 때 무엇을 바꿔야 하는지 바로 알 수 있습니다.
- **부족한 부분은 코드로 채웁니다.** 도형, 네온 셰이더, 파티클, 조명, 안개 같은 요소는 직접 만들 수 있습니다. 사이버펑크의 분위기는 모델링보다 **조명, 블룸, 안개, 반사**에서 많이 나옵니다.
- **진행 순서:** 처음에는 그레이박스(단색 도형)로 모든 시스템을 완성하고 재미를 검증합니다. 공개 에셋은 그 뒤에 입힙니다.

## 8. 기술 설계 개요

### 엔진: Godot 4.5
- **언어:** GDScript (필요하면 성능이 중요한 부분만 나중에 다른 방식으로 교체)
- **렌더러:** Forward+ (볼류메트릭 안개, 글로우, 반사 등 네온 분위기에 필요한 기능 포함)
- **네트워크:** Godot 내장 멀티플레이 기능(ENet 기반 LAN 통신, 노드 동기화)
- **테스트:** 화면 없이 실행하는 자동 테스트, 그리고 게임 두 개를 띄워 접속시키는 코옵 테스트
- **작업 흐름:** 씬과 데이터가 모두 텍스트 파일이라 제가 직접 작성하고 실행해 검증합니다. 사용자는 Godot 에디터에서 플레이 테스트를 합니다.

### 아키텍처 원칙
1. **데이터와 로직 분리:** 무기, 임플란트, 퀵핵, 적, 아이템, 대화, 출신을 **데이터 파일**(Godot Resource)로 정의합니다. 밸런스를 바꿀 때 코드를 고치지 않아도 됩니다.
2. **컴포넌트 조합:** `Health`, `Damageable`, `Hackable`, `Interactable`, `Detectable` 같은 작은 컴포넌트를 조합해 적, 장치, 문을 만듭니다.
3. **이벤트로 느슨한 결합:** 시스템끼리 직접 참조하지 않고 이벤트(예: `enemy_killed`, `alert_changed`)로 통신합니다. 퀘스트와 평판 시스템은 이 이벤트를 듣기만 합니다.
4. **상태 머신:** 플레이어 이동 상태와 적 AI(경계 단계)는 명시적인 상태 머신으로 구현해 동작을 예측하고 디버깅하기 쉽게 합니다.
5. **구역 단위 로딩:** 구역 하나가 씬 하나입니다. 구역을 떠날 때 그 구역의 상태(처치한 적, 열린 문, 주운 아이템)를 저장하고, 다시 들어올 때 복원합니다.
6. **저장 가능한 상태 분리:** 저장할 데이터(출신, 인벤토리, 평판, 퀘스트 진행, 구역 상태, 월드 플래그)는 엔진 객체와 분리된 단순한 데이터 구조로 두고 JSON으로 저장합니다. 캐릭터 데이터와 월드 데이터는 파일을 나눕니다(§5.2).
7. **입력과 판정 분리:** 플레이어 입력은 "의도"(이동, 사격, 해킹 시도)로만 보내고, 결과는 호스트가 판정합니다. 싱글 플레이에서도 같은 경로를 탑니다.

### 시스템 구성 (예정)
```
Core/        # 이벤트 버스, 저장, 구역 전환, 유틸
Net/         # 호스트·참여, 동기화, 판정 요청
Player/      # 이동, 카메라, 입력, 상호작용
Combat/      # 무기, 데미지, 체력
AI/          # 적 상태머신, 감지, 순찰
Hacking/     # 스캔, 퀵핵, RAM, 장치
Cyberware/   # 임플란트, 슬롯, 스탯 수정자, 리스·할부
Inventory/   # 아이템, 인벤토리, 상점
Narrative/   # 출신, 대화, 퀘스트, 평판, 월드 플래그
UI/
```

## 9. 로드맵 (마일스톤)

각 마일스톤 끝에 사용자가 직접 플레이하며 검수합니다. M1부터는 매번 **2인 LAN 코옵에서도 동작하는지** 함께 확인합니다.

| # | 마일스톤 | 결과물 / 검수 포인트 |
|---|---|---|
| M0 | **기반** | Godot 프로젝트 구조, 코딩 규칙, 자동 테스트 환경, 이 문서 확정 |
| M1 | **플레이어 컨트롤러 + 네트워크 뼈대** | 그레이박스 테스트 맵에서 이동과 카메라의 "손맛" 확인, LAN 방 만들기·참여, 2인 이동 동기화 |
| M2 | **전투 기초** | 무기 3종, 체력·피해, 과녁과 단순 적 |
| M3 | **적 AI와 잠입** | 순찰, 감지, 경계 단계, 은신 제압 |
| M4 | **해킹** | 스캔 모드, 퀵핵, 장치 해킹, 적 넷러너 |
| M5 | **성장** | 인벤토리, 사이버웨어, 상점, 리퍼닥, 리스와 빚 |
| M6 | **서사 시스템** | 출신, 대화, 퀘스트, 평판, 월드 플래그, 저장, 구역 전환 |
| M7 | **구역 제작과 콘텐츠** | 거점과 하역지구 그레이박스, 도입부 3종, 메인 의뢰와 사이드 의뢰 배치 |
| M8 | **룩과 폴리싱** | 공개 에셋 적용, 조명, VFX, 사운드, UI 다듬기 |

> 순서 원칙: **"손맛 → 시스템 → 콘텐츠 → 겉모습"**. 이동과 사격이 재미없으면 그 위의 모든 것이 재미없습니다.
