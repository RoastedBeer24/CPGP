## 1. 전제 조건

| 항목 | 결정 |
|---|---|
| 장르 | 1인칭 액션 RPG (사이버펑크), **구역형 반오픈월드**. V로 **3인칭 전환** 가능 |
| 플레이 인원 | **싱글 플레이 + LAN 코옵(2~3명)** (§5) |
| 엔진 | **Godot 4.5** (GDScript, Forward+ 렌더러) |
| 제목 | **CyberUniverse** |
| 톤 | **진지한 누아르** |
| 아트풍 | **서브컬처풍** (애니메이션풍 셀 셰이딩, §7.4) |
| 시작 연도 | **2048년** |
| 참고작 | **사이버펑크 2077** (전투 감각 포함) |
| 1차 목표 | **버티컬 슬라이스**: 거점 1곳과 작전 구역 1곳, 플레이 30~60분 분량 |
| 에셋 | **공개(무료) 에셋만 사용**, 라이선스 종류 무관 (§7.3) |
| 배포 | **상업화하지 않음.** 가족끼리만 플레이 |
| 역할 분담 | 개발(코드·구조·데이터): Claude / 기획 보조·검수·플레이 테스트: 사용자 |
| 플랫폼 | PC (Windows), 키보드·마우스 우선, 게임패드는 2순위 |

### 최우선 원칙: 그래픽보다 게임성
- 판단이 갈릴 때는 항상 **플레이가 더 재미있어지는 쪽**을 고릅니다. 그래픽 품질은 "읽기 쉽고 분위기가 전달되는" 수준이면 충분합니다.
- 시각 요소의 목표는 **가독성**입니다. 적과 엄폐물, 해킹 가능한 대상, 이동 경로가 한눈에 구분되어야 합니다.
- 그래서 개발 시간은 이동, 사격, 해킹, 선택의 결과처럼 **플레이어가 직접 만지는 것**에 먼저 씁니다.

## 2. 하이 콘셉트 (초안)

> **"태어날 때부터 등록된 나라에서, 당신은 누구로 살아남을 것인가."** (제안)

- **제목:** CyberUniverse
- **톤:** 진지한 누아르. 비, 네온, 고독, 도덕적으로 회색인 선택. 농담은 인물의 냉소 정도로만 둡니다.
- **배경:** **2048년**, 기업 중심 왕정국가 **네오조선**(현재의 대한민국 자리, [01-world.md](01-world.md))의 해안 거대도시 **"네오 부산(Neo-Busan)"**. 국제 항만 위로 고가도로와 고층 주거 블록이 겹겹이 쌓이고, 그 위에 기업 타워가 섭니다. 항만은 밀수와 데이터 거래의 중심지입니다. 도시는 높이에 따라 계층이 나뉘고, 이 구조가 **수직 탐험**과 연결됩니다.
- **주인공:** 외형을 커스터마이즈할 수 있습니다. **출신은 세 갈래** 중 하나를 고릅니다(§2.1). 출신마다 네오 부산과의 관계가 다르며, 각자의 계기로 이 도시에서 새 삶을 시작합니다. 도입부가 끝나면 의뢰를 받아 일하는 **해결사**가 됩니다.
- **핵심 갈등:** 기업, 국가, 범죄 조직이 얽힌 도시에서 **누구 편에 서서 살아남을 것인가**의 선택입니다([02-city-factions.md](02-city-factions.md)). 이것이 선택과 평판 시스템이 됩니다.

### 2.1 출신 세 갈래

출신마다 **네오 부산과의 관계가 다릅니다.** 둘은 바깥에서 들어오고, 하나는 원래 이 도시 사람입니다. 도입부는 "네오 부산에서 새 삶이 시작되는 계기"이고, 출신에 따라 그 장면과 사정이 달라집니다. 자세한 배경은 [01-world.md §5](01-world.md)에 있습니다.

출신은 **도입부 장면**, **고유 대화 선택지**, **NPC의 첫인상**만 바꿉니다. 능력이나 빌드에는 영향을 주지 않습니다.

| 출신 | 배경 (확정) | 네오 부산과의 관계 |
|---|---|---|
| **공무원** | **네오 서울**에서 제법 높은 직위에 있었으나, **꼬리 자르기**를 당해 버려짐. 권력의 작동 방식과 관료의 말투를 앎 | 외지인. 위에서 떨어져 내려온 사람 |
| **부랑자** | 원래부터 **네오 부산의 거리 출신**. 도시의 밑바닥과 사람을 앎 | 토박이. 처음부터 밑에 있던 사람 |
| **스캐빈저** | 네오 부산 인근의 **"죽음의 땅"**에서 활동하다, **도시의 삶이 궁금해** 발을 들임. 기계와 고철을 보는 눈이 있음 | 외지인. 바깥에서 처음 들어온 사람 |

### 2.2 시작 임플란트: 주민등록 임플란트
- 세 출신 모두 **똑같이 주민등록 임플란트 하나만** 가진 채 시작합니다. 네오조선 국민은 모두 태어날 때부터 이 임플란트가 뇌에 삽입되어 있습니다.
- **기능:** 통역, 생명 활동 체크 같은 생활의 기본 기능을 합니다.
- **성격:** **정부의 통제 아래 관리되는 신분증**입니다. 누구나 달고 있는 것이라서, 초반에는 **사실상 언급되지 않습니다.** 능력 보너스도 없고 UI에서도 눈에 띄지 않습니다.
- **제약:** 정부의 전파망이 닿지 않는 곳에서는 작동하지 않습니다([01-world.md §3.2](01-world.md)).
- 전투와 해킹에 쓰는 사이버웨어는 모두 도입부 이후 **리퍼닥에서 구매**해 장착합니다.

## 3. 핵심 기둥 (Design Pillars)

네 가지 재미 축(전투, 해킹·잠입, 스토리·선택, 탐험·성장)을 **세 개의 기둥**으로 묶습니다. 기능을 추가할지 판단할 때 "이 기능이 기둥을 강화하는가?"를 기준으로 삼습니다.

### 기둥 1. 모든 문에는 세 개의 열쇠가 있다
**전투 · 해킹 · 잠입**
- 모든 목표에 최소 3가지 접근이 있습니다: **정면 돌파**(총·근접), **넷러닝**(원격 해킹), **우회**(잠입·대화·환경 이용).
- 세 방식은 서로 섞입니다. 예를 들어 카메라를 해킹해 끄고, 잠입으로 들어간 뒤, 들키면 전투로 전환합니다.

### 기둥 2. 몸이 곧 빌드다
**성장**
- 레벨업 수치보다 **사이버웨어 장착**이 플레이 방식을 바꿉니다. 이중 점프 다리, 단분자 와이어 팔, RAM 확장 OS 등이 예입니다.
- 사이버웨어는 사이버펑크 2077처럼 **리퍼닥에서 돈을 주고 구매**합니다.
- 몸이 견딜 수 있는 **사이버웨어 용량**에 한도가 있어서, 모든 임플란트를 다 달 수는 없습니다. 무엇을 달고 무엇을 포기할지가 빌드가 됩니다 (제안).

### 기둥 3. 도시는 기억한다
**스토리 · 선택 · 탐험**
- 선택은 **세력 평판**, **구역 상태**(경비 강화, 상점 폐쇄 등), **NPC의 반응**으로 되돌아옵니다.
- 탐험 원칙은 **"넓이보다 밀도"**입니다. 작은 구역을 수직으로 촘촘하게 만들고, 숨은 경로와 데이터 조각, 사이드 의뢰를 곳곳에 둡니다.

## 4. 월드 구조: 구역형 반오픈월드

끊김 없는 하나의 거대한 맵 대신, 도시를 **여러 구역**으로 나눕니다. 데우스 엑스: 휴먼 레볼루션의 허브 구조와 비슷합니다.

- **구역 안에서는 자유롭게** 돌아다닙니다. 의뢰 순서, 접근 경로, 탐험 범위를 플레이어가 정합니다.
- **구역 사이 이동**은 엘리베이터, 지하철, 검문소 같은 **전환 지점**을 거치며 짧은 로딩을 둡니다.
- **구역의 종류**
  - **거점 구역:** 안전한 곳. 상점, 리퍼닥, 의뢰 중개인, 은신처가 있습니다. 전투는 없습니다.
  - **작전 구역:** 의뢰를 수행하는 곳. 경비, 적, 해킹 대상, 숨은 경로가 있습니다.
- **구역 상태가 저장됩니다.** 처치한 적, 열린 문, 바뀐 평판이 구역을 다시 찾아도 유지됩니다.

이 방식은 범위가 커지는 위험을 줄이고, 구역 하나하나를 촘촘하게 만들 수 있게 해줍니다. 엔진의 대형 맵 처리 기능에도 의존하지 않습니다.

## 5. 플레이 인원: 싱글 + LAN 코옵

기본은 **혼자서도 완결되는 싱글 플레이**이고, 같은 네트워크(LAN)에 있는 가족이 **합류할 수 있는** 구조입니다. **코옵에서는 메인 스토리를 진행할 수 없습니다.** 코옵은 사이드 의뢰, 자유 탐험, 전투를 함께 즐기는 모드입니다.

### 5.1 처음부터 멀티플레이를 염두에 두는 이유
멀티플레이는 나중에 붙이기가 가장 어려운 기능입니다. 싱글 전용으로 짠 코드를 나중에 코옵용으로 바꾸려면 거의 다시 써야 합니다. 그래서 **M1부터 모든 게임플레이 코드를 네트워크를 전제로** 작성합니다. 싱글 플레이는 "혼자 호스트하는 코옵"으로 처리해서, 두 방식이 같은 코드로 돌아가게 합니다.

### 5.2 기본 구조
- **호스트 방식:** 한 플레이어의 게임이 서버 역할을 겸합니다. 별도 서버는 없습니다.
- **판정은 호스트가:** 적 AI, 피해 계산, 해킹 성공 여부, 퀘스트 진행, 구역 상태는 호스트가 결정하고 다른 플레이어에게 전달합니다. 동기화가 어긋나는 문제를 줄이는 표준적인 방식입니다.
- **세이브:** 월드 진행(퀘스트, 평판, 구역 상태)은 **호스트의 세이브**에 저장됩니다. 캐릭터(출신, 외형, 사이버웨어, 인벤토리, 돈)는 **각 플레이어가 자기 것을 들고** 참여합니다.

### 5.3 코옵 때문에 달라지는 설계
| 요소 | 코옵에서의 처리 |
|---|---|
| 메인 스토리 | **진행 불가.** 메인 의뢰는 코옵 중에 시작하거나 진행할 수 없음 (확정) |
| 사망 | **싱글과 같은 사망 판정.** 다운이나 부활 같은 별도 상태는 없음 (확정) |
| 사망 후 처리 | 사망한 플레이어는 관전하다가, 의뢰가 끝나거나 생존자가 거점으로 돌아오면 함께 복귀. 전원 사망 시 마지막 저장 지점에서 재시작 (제안) |
| 시간 조작 효과 | 슬라이스에는 시간 감속 기능이 없음. 나중에 이런 효과가 생기면 **세상 전체를 느리게** 하는 방식 그대로 구현 (확정) |
| 일시정지 | 코옵 중에는 메뉴를 열어도 게임이 멈추지 않음 (제안) |
| 대화와 선택 | 사이드 의뢰의 대화는 대화를 시작한 플레이어가 선택 (제안) |
| 평판과 결과 | 사이드 의뢰의 결과는 호스트 월드에 반영 (제안) |
| 난이도 | 참여 인원에 따라 적의 수와 체력을 조정 (제안) |

### 5.4 범위
- **포함:** LAN 안에서 방 만들기와 참여, 인원 **2~3명**
- **제외:** 인터넷 매치메이킹, 전용 서버, PvP, 음성 채팅
- **검증 방법:** 이 개발 환경에서 게임을 여러 개 띄워 서로 접속시키는 자동 테스트로 동기화를 확인합니다. 실제 PC 간 LAN 테스트는 사용자가 합니다.

`[결정 필요]` §5.3에서 (제안)으로 표시한 항목, 특히 사망 후 처리 방식이 괜찮은가요?

## 6. 코어 루프

```
[30초 루프]  감지 → 접근 선택 → 실행 → 상황 변화에 적응
              (스캔)  (총/해킹/잠입)        (발각, 증원, RAM 부족…)

[20분 루프]  거점에서 의뢰 수락 → 작전 구역 이동 → 정찰 → 침투/교전 → 목표 달성
                 ↑                                                      ↓
              평판 변화 ← 리퍼닥에서 사이버웨어 구매·장착 ← 거점 복귀 ← 돈·부품

[캠페인]     세력 사이에서 줄타기 → 세력 선택 → 결말 분기 (메인 스토리는 보류)
```

## 7. 버티컬 슬라이스 범위

### 7.1 포함 (Must)
| 영역 | 내용 |
|---|---|
| 구역 | **거점 구역 1곳**(소형: 상점, 리퍼닥, 중개인, 은신처) + **작전 구역 1곳: "하역지구"**(약 250×250m, 지상·골목·옥상·지하 3~4층 구조). 구역 전환 1개 |
| 출신 | 세 출신 모두 선택 가능. "네오 부산에서 새 삶이 시작되는" 공통 도입부에 출신별 장면과 대화를 다르게 둠 |
| 코옵 | LAN 방 만들기·참여, 2~3인 동시 플레이, 사이드 의뢰 함께 진행 |
| 이동 | 걷기, 달리기, 웅크리기, 슬라이딩, 벽 오르기(맨틀), 이중 점프(임플란트) |
| 전투 | **사이버펑크 2077식 RPG 슈터**. 무기 3종(권총, 산탄총, 팔 내장형 근접 블레이드), 히트스캔 사격, 반동, 부위별 피해, 장갑, 피해 수치 표시, 회피 대시 |
| 적 AI | 3종: 일반 경비, 중장갑병, 적 넷러너(플레이어를 역해킹) |
| 잠입 | 시야 원뿔, 경계 단계(무경계 → 의심 → 수색 → 전투), 은신 제압, 시체 숨기기 |
| 해킹 | 스캔 모드, RAM 기반 퀵핵 4종(카메라 차단, 주의 분산, 과열, 무기 오작동), 장치 해킹(문, 포탑) |
| 성장 | 사이버웨어 슬롯 5부위, 구매형 임플란트 8종, 사이버웨어 용량, 인벤토리, 상점, 리퍼닥 |
| 서사 | 메인 의뢰 1개(결말 분기 2~3개), 사이드 의뢰 2개, 대화 트리와 능력·출신 체크 |
| 세력 | **아틀라스 해운**과 **흑조** 2개 세력의 평판 수치. 평판에 따라 대화, 가격, 적대 여부가 바뀜 |
| 시스템 | 저장/불러오기, 일시정지, 설정(감도, 볼륨, 키 바인딩) |

### 7.2 제외 (Won't, 슬라이스 이후 검토)
차량, 끊김 없는 대형 맵(구역 간 로딩으로 대체), 낮/밤 사이클, 제작(크래프팅), 성우 음성, 로맨스, 인터넷 멀티플레이, 경찰 수배 시스템, 세밀한 캐릭터 외형 편집(슬라이스에서는 프리셋 몇 개)

> 제외 목록이 기능 목록만큼 중요합니다. 오픈월드 계열은 범위가 커지다 실패하는 경우가 가장 흔합니다.

### 7.3 에셋 정책: 공개 에셋만 사용
- **라이선스:** 상업화하지 않고 가족끼리만 플레이하므로, 무료로 공개된 에셋이면 **라이선스 종류와 관계없이** 사용합니다. 출처 표기를 요구하는 에셋은 크레딧에 표기합니다.
- **저장소 주의:** 일부 에셋은 "원본 파일 재배포 금지" 조건이 있습니다. 이 저장소가 공개 상태라면 그런 에셋은 저장소에 올리지 않고 받는 방법만 기록합니다.
- **주요 출처 후보**
  - 캐릭터: VRoid Hub의 공개 VRM 모델(모델마다 이용 조건 확인)
  - 3D 모델: Kenney, Quaternius
  - 텍스처와 HDRI: Poly Haven, ambientCG
  - 효과음: Freesound(CC0 필터), Kenney Audio
  - 음악, 폰트, 기타: OpenGameArt, Google Fonts(OFL)
- **기록:** 사용하는 에셋마다 출처, 작가, 라이선스를 `docs/assets.md`에 기록하고, 게임 크레딧에도 표시합니다.
- **부족한 부분은 코드로 채웁니다.** 도형, 네온 셰이더, 파티클, 조명, 안개 같은 요소는 직접 만들 수 있습니다. 사이버펑크의 분위기는 모델링보다 **조명, 블룸, 안개, 반사**에서 많이 나옵니다.
- **진행 순서:** 처음에는 그레이박스(단색 도형)로 모든 시스템을 완성하고 재미를 검증합니다. 공개 에셋은 그 뒤에 입힙니다.

### 7.4 아트풍: 서브컬처풍
- **방향:** 애니메이션풍 캐릭터와 **셀 셰이딩**(만화처럼 명암을 단계로 끊는 표현), 외곽선을 기본으로 합니다. 여기에 사이버펑크 네온, 비, 안개를 얹습니다.
- **캐릭터:** VRoid 계열 VRM 모델을 쓰면 무료 공개 모델이 많고, 외형 프리셋을 만들기도 쉽습니다. Godot에는 VRM 모델을 불러오는 공개 애드온이 있습니다.
- **배경:** 배경 에셋은 화풍이 제각각이므로, 공통 툰 셰이더를 씌워 캐릭터와 톤을 맞춥니다. 디테일이 적은 로우폴리 에셋이 셀 셰이딩과 잘 어울립니다.
- **누아르 톤과의 조화:** 밝은 애니메이션 색감보다는 어두운 배경에 네온 원색이 튀는 대비를 씁니다.
- **1인칭 시점:** 플레이어 자신의 몸은 손과 무기 정도만 보이므로, 캐릭터 모델 품질은 주로 NPC와 적, 코옵 동료에게서 드러납니다. 3인칭(어깨 너머)으로 바꾸면 내 캐릭터도 보입니다.

## 8. 기술 설계 개요

### 엔진: Godot 4.5
- **언어:** GDScript (필요하면 성능이 중요한 부분만 나중에 다른 방식으로 교체)
- **렌더러:** Forward+ (볼류메트릭 안개, 글로우, 반사 등 네온 분위기에 필요한 기능 포함)
- **셰이딩:** 직접 작성하는 툰 셰이더와 외곽선 처리, VRM 캐릭터용 공개 애드온
- **네트워크:** Godot 내장 멀티플레이 기능(ENet 기반 LAN 통신, 노드 동기화)
- **테스트:** 화면 없이 실행하는 자동 테스트, 그리고 게임 두 개를 띄워 접속시키는 코옵 테스트
- **작업 흐름:** 씬과 데이터가 모두 텍스트 파일이라 제가 직접 작성하고 실행해 검증합니다. 사용자는 Godot 에디터에서 플레이 테스트를 합니다.

### 아키텍처 원칙
1. **데이터와 로직 분리:** 무기, 임플란트, 퀵핵, 적, 아이템, 대화, 출신을 **데이터 파일**(Godot Resource)로 정의합니다. 밸런스를 바꿀 때 코드를 고치지 않아도 됩니다.
2. **컴포넌트 조합:** `Health`, `Damageable`, `Hackable`, `Interactable`, `Detectable` 같은 작은 컴포넌트를 조합해 적, 장치, 문을 만듭니다.
3. **이벤트로 느슨한 결합:** 시스템끼리 직접 참조하지 않고 이벤트(예: `enemy_killed`, `alert_changed`)로 통신합니다. 퀘스트와 평판 시스템은 이 이벤트를 듣기만 합니다.
4. **상태 머신:** 플레이어 이동 상태와 적 AI(경계 단계)는 명시적인 상태 머신으로 구현해 동작을 예측하고 디버깅하기 쉽게 합니다.
5. **구역 단위 로딩:** 구역 하나가 씬 하나입니다. 구역을 떠날 때 그 구역의 상태(처치한 적, 열린 문, 주운 아이템)를 저장하고, 다시 들어올 때 복원합니다.
6. **저장 가능한 상태 분리:** 저장할 데이터(출신, 인벤토리, 평판, 퀘스트 진행, 구역 상태, 월드 플래그)는 엔진 객체와 분리된 단순한 데이터 구조로 두고 JSON으로 저장합니다. 캐릭터 데이터와 월드 데이터는 파일을 나눕니다(§5.2).
7. **이동은 각자, 판정은 호스트:** 자기 캐릭터의 이동과 시점은 반응성을 위해 각 플레이어가 직접 계산하고 위치를 공유합니다. 피해, 적 AI, 해킹 성공 여부, 상호작용 결과처럼 **게임 결과를 바꾸는 판정은 호스트**가 합니다. 싱글 플레이에서도 같은 경로를 탑니다.

### 시스템 구성 (예정)
```
Core/        # 이벤트 버스, 저장, 구역 전환, 유틸
Net/         # 호스트·참여, 동기화, 판정 요청
Player/      # 이동, 카메라, 입력, 상호작용
Combat/      # 무기, 데미지, 체력
AI/          # 적 상태머신, 감지, 순찰
Hacking/     # 스캔, 퀵핵, RAM, 장치
Cyberware/   # 임플란트, 슬롯, 용량, 스탯 수정자
Inventory/   # 아이템, 인벤토리, 상점
Narrative/   # 출신, 대화, 퀘스트, 평판, 월드 플래그
UI/
```
